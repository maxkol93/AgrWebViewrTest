# Деплой

Обновление приложения — **одной командой** или **одним push**. Обновляются сразу и
сайт (`index.html`, `script.js`), и логика (Cloud Function в `backend/`).

Стек: Yandex Object Storage (хранилище + хостинг сайта) + Yandex Cloud Function (бэкенд).

## Два стенда

| Стенд    | Ветка  | Бакет            | Функция             | Кто видит          |
|----------|--------|------------------|---------------------|--------------------|
| **dev**  | `dev`  | `agr-viewer-dev` | `agr-viewer-api-dev`| только вы          |
| **prod** | `main` | `agr-viewer`     | `agr-viewer-api`    | пользователи       |

Стенды полностью независимы: свои данные, свой `ADMIN_TOKEN`, свой URL. Дев-сайт
помечен оранжевым бейджем **DEV** сверху, префиксом `[DEV]` во вкладке и суффиксом
в версии (`v0.2.7-dev`) — спутать вкладки невозможно.

## Как обновить приложение (каждый день)

Рабочий цикл: правки → дев → проверка вживую → прод.

```powershell
git switch dev
git add -A; git commit -m "обновление"; git push     # → дев-стенд
# …проверили на https://agr-viewer-dev.website.yandexcloud.net…
git switch main; git merge dev; git push             # → прод
```

GitHub Actions сам определяет стенд по ветке: `dev` → дев, `main` → прод.
Статус — вкладка **Actions**. Пуш в любую другую ветку ничего не деплоит.

### Локально, одной командой

```powershell
.\deploy.ps1                # дев (по умолчанию)
.\deploy.ps1 -Target prod   # прод, спросит подтверждение
```

Разные стенды читают разные конфиги (`config.dev.ps1` / `config.local.ps1`),
поэтому перепутать их нельзя. Локальный и «пушевый» деплой взаимозаменяемы.

### Разово задеплоить любую ветку куда угодно

Actions → **Deploy (Yandex Cloud)** → Run workflow → выбрать ветку и стенд.

### Версия на сайте

Внизу справа мелким полупрозрачным шрифтом показывается версия `v<major.minor>.<patch>`:
- **major.minor** — в файле `VERSION` (напр. `0.2`). Поднимаешь **вручную** при смене функционала (`0.3`, `1.0`…).
- **patch** — считается автоматически = число коммитов с момента последнего изменения `VERSION`. То есть после каждого пуша `+1`, а при ручном поднятии `VERSION` сбрасывается в `0` (`v0.3.0`).
- на деве добавляется суффикс стенда: `v0.3.0-dev`.

Ничего вручную в HTML править не нужно — версия подставляется при деплое.

## Данные на деве

Чтобы тестировать на реальных моделях, данные прода копируются в дев одной кнопкой:
Actions → **Sync prod → dev (данные)** → Run workflow.

> Кнопка в Actions появляется только после того, как workflow попал в `main`:
> GitHub показывает ручной запуск исключительно из дефолтной ветки. До мержа
> запускайте синхронизацию локально (команды ниже, с выключенным VPN).

- `dry` (по умолчанию **включён**) — только показать план, ничего не менять. Снимите, чтобы копировать по-настоящему.
- `prune` — заодно удалить в деве то, чего в проде уже нет. По умолчанию выключено.

Копируются модели, HDR-карты и каталог; **сайт не копируется** — он деплоится из
репозитория, иначе дев затёрся бы прод-версией. Копирование серверное (S3 CopyObject):
байты не выкачиваются, 30 МБ переезжают мгновенно и не тратят трафик. Уже совпадающие
объекты (размер + ETag) пропускаются, так что повторный запуск дешёвый.

Направление **зашито в workflow**: только прод → дев. Обратно данные не поедут, даже
если очень постараться. Дополнительно сам скрипт откажется писать в бакет, в имени
которого нет `dev`/`test`/`stage`.

Локально то же самое:

```powershell
. .\deploy\config.local.ps1
$env:SRC_BUCKET="agr-viewer"; $env:DEST_BUCKET="agr-viewer-dev"
node deploy/sync-buckets.mjs --dry
node deploy/sync-buckets.mjs
```

## Разовая настройка

Ниже — то, что делается **один раз**. После этого обновление всегда идёт командами выше.

### 0. Что где хранится

```
бакет agr-viewer/
├── index.html, script.<hash>.js                ← сайт (заливает деплой)
├── vendor/                                     ← three.js, Draco, шрифт (заливает деплой)
├── models.json, projects.json, subprojects.json ← создаёт функция/импорт каталога
├── models/                                      ← .glb, кладёт функция при загрузке
└── environments/                               ← HDR-карты (залить вручную один раз)
```

`vendor/` — библиотеки, которые раньше тянулись с unpkg.com и gstatic.com. У части
российских провайдеров эти домены деградируют, и сайт вис на «загрузке модели»,
поэтому всё раздаётся со своего бакета. Версии прибиты в `deploy/package.json`;
деплой заливает только изменившиеся файлы. Подробности — `docs/perf-loading-plan.md`.

Имя `script.<hash>.js` меняется вместе с содержимым, поэтому файл кэшируется на год;
`index.html` остаётся `no-cache`. Старые сборки скрипта деплой убирает сам.

Модель данных: **Проект → Подпроект (Очередь/Этап) → Модель**. У подпроекта есть
уникальный **код** — по нему открывается сайт: `…/?model=<код>`. У модели есть дата
(`modelDate`), необязательное имя версии и комментарий; несколько моделей в одном
подпроекте = версии (в UI выбираются селектором, по умолчанию самая свежая).
Если по коду нет моделей — на сайте «Модель не найдена!».

Структуру папок создавать вручную не нужно — она появляется сама при заливке.
HDR-карты (`environments/*.hdr`) залейте один раз через консоль.

### 1. Бакет Object Storage

Консоль → **Object Storage** → создать бакет (напр. `agr-viewer`):
- Доступ на чтение объектов — **публичный** (браузер качает `.glb` и `models.json` напрямую).
- Вкладка **Веб-сайт** → включить хостинг: главная и страница ошибок — `index.html`.
- Вкладка **CORS** → правило:

```json
[{ "AllowedOrigins": ["*"], "AllowedMethods": ["GET","PUT","HEAD"],
   "AllowedHeaders": ["*"], "ExposeHeaders": ["ETag"], "MaxAgeSeconds": 3000 }]
```

Сайт будет доступен по адресу `https://<бакет>.website.yandexcloud.net`.

### 2. Сервисный аккаунт и ключ

IAM → создать сервисный аккаунт (роль `storage.editor`) → **создать статический ключ**.
Сохраните `accessKeyId` и `secretAccessKey` — понадобятся в конфиге деплоя и функции.

### 3. Cloud Function

Консоль → **Cloud Functions** → создать функцию (напр. `agr-viewer-api`),
среда `nodejs18`, точка входа `index.handler`, сделать **публичной**.
Код и переменные окружения зальёт деплой — руками ничего собирать/зиповать не нужно.
Запомните URL функции вида `https://functions.yandexcloud.net/d4eXXXXX`.

### 4A. Настройка локального деплоя (`.\deploy.ps1`)

1. Установите **Node.js 18+** и **Yandex CLI**:
   ```powershell
   iex (New-Object Net.WebClient).DownloadString('https://storage.yandexcloud.net/yandexcloud-yc/install.ps1')
   ```
   Перезапустите терминал, затем `yc init` (авторизация + выбор облака/каталога).
2. Скопируйте конфиг и заполните его своими значениями:
   ```powershell
   Copy-Item deploy\config.example.ps1 deploy\config.local.ps1
   notepad deploy\config.local.ps1
   ```
   `config.local.ps1` в `.gitignore` — секреты в git не попадут.

Готово: теперь `.\deploy.ps1` работает.

### 4B. Настройка автодеплоя (GitHub Actions)

Секреты делятся на два уровня. **Общие для стендов** — в
**Settings → Secrets and variables → Actions**:

| Секрет                    | Значение                                            |
|---------------------------|-----------------------------------------------------|
| `S3_ACCESS_KEY_ID`        | из статического ключа сервисного аккаунта          |
| `S3_SECRET_ACCESS_KEY`    | из статического ключа сервисного аккаунта          |
| `YC_FOLDER_ID`            | ID каталога в Yandex Cloud                          |
| `YC_SA_JSON_CREDENTIALS`  | JSON авторизованного ключа сервисного аккаунта¹    |

**Различающиеся** — в **Settings → Environments**, отдельно в `prod` и в `dev`
(имена одинаковые, значения разные — поэтому workflow один на оба стенда):

| Секрет                    | prod                                   | dev                                        |
|---------------------------|----------------------------------------|--------------------------------------------|
| `S3_BUCKET`               | `agr-viewer`                           | `agr-viewer-dev`                           |
| `STORAGE_BASE_URL`        | `…/agr-viewer`                         | `…/agr-viewer-dev`                         |
| `API_BASE_URL`            | URL прод-функции                       | URL дев-функции                            |
| `YC_FUNCTION_NAME`        | `agr-viewer-api`                       | `agr-viewer-api-dev`                       |
| `ADMIN_TOKEN`             | пароль на загрузку                     | **свой**, отдельный                        |

Плюс переменные (не секреты): `SITE_URL` в каждом окружении — для ссылки в логе;
`PROD_BUCKET` и `DEV_BUCKET` на уровне репозитория — для синхронизации данных.

> **Важно:** пяти секретов из второй таблицы не должно остаться на уровне
> репозитория. Иначе забытый дев-секрет молча подменится прод-значением и
> дев-деплой уедет в прод. Скрипт настройки (см. ниже) удаляет их сам.

¹ Создать: `yc iam key create --service-account-name <sa> --output key.json`,
затем вставить содержимое `key.json` в секрет. Сервисному аккаунту нужны роли
`storage.editor` и `functions.editor` (или `editor`).

Готово: теперь `git push` в `main` деплоит прод, в `dev` — дев.

### 5. Дев-стенд — двумя скриптами

Всё, что описано выше, для дева делается автоматически.

```powershell
# 0) только если нет deploy\config.local.ps1 — VPN ВЫКЛЮЧЕН
.\deploy\bootstrap-config.ps1
```
Восстанавливает конфиг прода из облака: деплой кладёт `S3_BUCKET`, ключи сервисного
аккаунта и `ADMIN_TOKEN` в переменные окружения Cloud Function — оттуда и читает.
Нужен, если стенд настраивался только через GitHub Actions: секреты GitHub обратно
не читаются. Только чтение, в облаке ничего не меняет.

```powershell
# 1) VPN ВЫКЛЮЧЕН (yc и Object Storage ходят в ru-central1)
.\deploy\setup-dev-stand.ps1
```
Создаёт бакет `agr-viewer-dev` (публичное чтение, хостинг, CORS) и публичную функцию
`agr-viewer-api-dev`, генерирует отдельный `ADMIN_TOKEN`, пишет `deploy\config.dev.ps1`
и `deploy\dev-stand.out.json`. Идемпотентно: если что-то уже создано — просто дочитает.

```powershell
# 2) VPN ВКЛЮЧЁН (нужен github.com)
.\deploy\setup-dev-github.ps1
```
Создаёт окружения `prod` и `dev`, раскладывает по ним секреты из локальных конфигов,
заводит переменные и убирает разъехавшиеся секреты с уровня репозитория.

```powershell
# 3) первый деплой дева
git switch -c dev
git push -u origin dev
```

Дальше — Actions → **Sync prod → dev (данные)**, чтобы налить реальные модели.

> Если хочется страховки от случайного пуша в `main`: Settings → Environments →
> `prod` → **Required reviewers** (себя). Тогда прод-деплой встанет на подтверждение.

## Как это работает и сколько стоит

- Смотреть модели может любой без пароля (по коду `?model=<код>`).
- **Админка** — клавиша **`U`** на десктопе переключает режим юзер↔админ. Без пароля
  сперва спросит `ADMIN_TOKEN` (сохранит в `localStorage` под ключом `agrAdminToken`;
  сброс — `localStorage.removeItem('agrAdminToken')`). В админке: загрузка/удаление
  моделей (проект → подпроект → дата/версия/комментарий) и каталог (проекты/подпроекты, коды).
- Стоимость под небольшую нагрузку: **≈ 20–60 ₽/мес** (хранилище + трафик; функция в бесплатном тире).

### Эндпоинты функции (один URL, маршрут в `?action=`)

- `GET  ?action=list` / `?action=projects` / `?action=subprojects` — списки (сайт читает JSON напрямую из бакета)
- `POST ?action=upload|commit|delete|update` (заголовок `X-Admin-Token`) — операции с моделями
- `POST ?action=project-create|project-rename|project-delete` — операции с проектами
- `POST ?action=subproject-create|subproject-update|subproject-delete` — операции с подпроектами
- `POST ?action=telemetry` — замеры загрузки от браузера посетителя, **без пароля** (см. ниже)

### Телеметрия загрузки

Сайт один раз за открытие шлёт событие с временем по фазам (index.html →
зависимости → каталог → скачивание `.glb` → разбор → первый кадр) плюс тип
соединения и класс устройства. Событие уходит через `sendBeacon`, в том числе
когда человек закрывает вкладку, не дождавшись модели, — этот случай (`abandoned`)
и есть та самая жалоба, только молча. Личных данных не сохраняем: ни IP, ни чего
бы то ни было ещё, что можно связать с человеком. Отключить у себя:
`localStorage.setItem('agrTelemetry','off')`.

События лежат в бакете отдельными файлами `telemetry/<дата>/*.json` (десятки байт
каждый) и между стендами не синхронизируются. Отчёт:

```powershell
. .\deploy\config.dev.ps1          # креды + бакет ДЕВА (для прода — config.local.ps1), VPN ВЫКЛЮЧЕН
node deploy/telemetry-report.mjs               # последние 7 дней
node deploy/telemetry-report.mjs --days 1
node deploy/telemetry-report.mjs --raw > events.json   # выгрузить как есть
node deploy/telemetry-report.mjs --file events.json    # разбирать потом, бакет не нужен
```

Когда данных накопится и они больше не нужны — можно удалить старые дни целиком:
это обычные объекты с префиксом `telemetry/<дата>/`.

### Импорт каталога проектов/подпроектов (из Excel)

Коды приходят извне (Excel). Парсинг делает разработчик и кладёт результат в
`docs/projects_codes.json` (массив `[{code, project, subproject}]`). Затем — заливка в бакет:

```powershell
. .\deploy\config.dev.ps1          # креды + бакет ДЕВА (для прода — config.local.ps1)
node deploy/import-catalog.mjs             # идемпотентный мёрж (добавит новое, обновит по коду)
node deploy/import-catalog.mjs --dry       # показать, что изменится, без записи
node deploy/import-catalog.mjs --reset      # ПЕРВЫЙ прогон: пересобрать каталог с нуля
```

Через Actions: **Import catalog** → выбрать стенд (`dev` по умолчанию) и флаги.
Импорт бьёт в бакет выбранного стенда — сперва прогоняйте на деве.

Мёрж по коду: новые подпроекты добавляются, существующие обновляются; **подпроекты
никогда не удаляются** (в т.ч. с моделями). `--reset` отбрасывает старые плоские проекты
(модели при этом остаются в Unknown/Common и не трогаются).
